# Вимоги файлами (варіант `docs/`)

Ця тека потрібна, лише якщо ви, PM, обрали зберігати вимоги **файлами**, а не в issues (вибір — у README репо).
Усе робиться у вебінтерфейсі GitHub, без git і командного рядка. Назви кнопок нижче — з англійського інтерфейсу
GitHub; точну назву перевірте в інтерфейсі.

## Що де лежить

| Файл | Що це | Чи забирають розробники |
|---|---|---|
| `docs/product.md` | продукт: бачення, ролі й матриця прав, глосарій, roadmap, що поза scope | так |
| `docs/requirements/<NN>-<slug>.md` | одна вимога (зріз або фіча) | так |
| `docs/requirements/_template.md` | порожній шаблон вимоги — звідси копіюєте текст | ні |
| `docs/requirements/README.md` | ця інструкція | ні |
| `docs/drafts/<NN>-<slug>.md` | чернетка вимоги, яку ще рано віддавати розробникам (теку створюєте самі, за потреби) | ні |

Назва файлу вимоги: `NN` — дві цифри за порядком (`01`, `02`…), `slug` — кілька англійських слів малими літерами
через дефіс. Наприклад: `01-reserve.md`, `02-waiting-list.md`. Без пробілів і кирилиці. Номер файлу не змінюйте.

## Як створити вимогу

1. Відкрийте `docs/requirements/_template.md` і скопіюйте весь текст: кнопка **Copy raw file** над текстом файлу
   або **Raw** → виділити все → копіювати.
2. Поверніться в теку `docs/requirements` → **Add file** → **Create new file**.
3. У полі назви введіть ім'я файлу, наприклад `01-reserve.md` (ви вже в теці `docs/requirements/`).
4. Вставте скопійований текст і заповніть кожен розділ. Вкладка **Preview** показує, як це виглядатиме.
5. **Commit changes…** → повідомлення, наприклад «Вимога 01: резервування» → **Commit directly to the `main`
   branch** → **Commit changes**.

Кожен критерій приймання — один рядок (Enter усередині не натискайте), а його ID не повторюється в жодній іншій
вимозі репо.

Файл у `docs/requirements/` гілки `main` розробники заберуть при наступній синхронізації, тож створюйте його з
готовим текстом. **Чернетку** (наприклад, вимоги наступного зрізу для бонусу E) кладіть у теку `docs/drafts/`
(на головній сторінці репо **Add file** → **Create new file** → у полі назви `docs/drafts/02-<slug>.md`): її розробники не забирають. Коли настане час
— створіть файл у `docs/requirements/` з цим текстом, а чернетку видаліть.

## Як змінити вимогу

1. Відкрийте файл → олівець **Edit this file**.
2. Змініть текст у потрібному розділі. Змінений критерій зберігає свій ID; новий критерій отримує наступний вільний
   номер; прибраний — видаліть з «Критерії приймання» і запишіть у журнал, чому. Прибраний ID більше не
   використовуйте.
3. Додайте рядок у **«Журнал змін»**: `- 2026-10-18 — що змінилось — посилання на питання` (повна адреса issue
   «Питання до вимог» з адресного рядка).
4. **Commit changes…** → у полі повідомлення коміту — `Зміна: AC-RESERVE-02 — <адреса питання>` →
   **Commit directly to the `main` branch** → **Commit changes**.
5. Напишіть у чат команди «вимоги оновлено» з датою й переліком змінених критеріїв.

Самоперевірку за [`docs/checklist.md`](../checklist.md) записуйте рядком у «Журнал змін»:
`- 2026-10-16 — Перевірено за чеклістом: …`.

## Чого не робити у варіанті `docs/`

- Не створюйте issues «Вимога» і «Продукт»: якщо в репо є хоч одне відкрите issue з міткою `requirement`,
  розробники отримають вимоги з issues, а ваші файли проігнорують.
- Не перейменовуйте й не переносьте файли вимог: для розробників це виглядає як «одну вимогу прибрано, іншу додано».
- Не пишіть вимоги в `_template.md` чи в цей README — їх розробники не забирають.
- Питання розробників однаково приходять в issues «Питання до вимог» — відповідайте там.

## Приклад заповненої вимоги

Приклад з іншої області — міська бібліотека. Не копіюйте його, пишіть про свій продукт.

```markdown
# Вимога: резервування книжки

### Навіщо

Читачі дізнаються, чи є книжка, лише коли приходять до бібліотеки, і часто йдуть ні з чим.
Після цієї вимоги читач резервує вільний примірник онлайн і забирає його протягом 3 діб.

### Користувачі й ролі

- Читач (`reader`) — резервує книжки, бачить лише власні резервування.
- Бібліотекар (`librarian`) — бачить усі резервування, видає книжки за резервуванням.

### Основний сценарій

1. Читач знаходить книжку в каталозі і бачить, скільки вільних примірників.
2. Читач резервує книжку.
3. Бібліотекар бачить нове резервування в списку на видачу.
4. Читач приходить протягом 3 діб, бібліотекар видає книжку, резервування закривається.

### Критерії приймання

- AC-RESERVE-01: Дано читач без активних резервувань і книжка з 2 вільними примірниками. Коли читач резервує книжку. Тоді резервування має статус «очікує видачі», вільних примірників стає 1, а резерв діє 3 доби.
- AC-RESERVE-02: Дано читач, у якого вже 5 резервувань зі статусом «очікує видачі». Коли він резервує ще одну книжку. Тоді резервування не створюється, і читач бачить повідомлення «Не більше 5 резервувань одночасно».
- AC-RESERVE-03: Дано резервування, за яким книжку не видали протягом 3 діб. Коли минає третя доба. Тоді не пізніше ніж за 24 години резервування має статус «прострочено», а примірник знову вільний.
- AC-RESERVE-04: Дано два читачі з резервуваннями. Коли перший відкриває список своїх резервувань. Тоді він бачить лише власні резервування.

### Поза межами

- Черга на книжку без вільних примірників — окрема вимога наступного зрізу.
- Нагадування листом: читач бачить строк резерву лише в застосунку.

### Припущення

- Каталог книжок і кількість примірників уже є: їх вносить бібліотекар.
- Доба рахується за київським часом.
- Строк резерву рахуємо від моменту резервування з точністю до хвилини: 3 доби — це 72 години.

### Відкриті питання

- Чи може бібліотекар продовжити резерв понад 3 доби? (не в цьому зрізі)

### Журнал змін

- 2026-10-16 — створено
- 2026-10-16 — Перевірено за чеклістом: 1–16 так; до AC-RESERVE-03 додано «не пізніше ніж за 24 години»
- 2026-10-18 — AC-RESERVE-02: прострочені резервування не рахуються в ліміт 5 — питання https://github.com/<pm>/<team-slug>-spec/issues/7
```
